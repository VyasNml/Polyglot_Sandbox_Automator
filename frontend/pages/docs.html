Polyglot Sandbox Automator

The Polyglot Sandbox Automator (PSA) is a backend-centric platform for executing arbitrary code across multiple programming languages inside isolated Docker containers. It is designed for use cases such as online judges, code playgrounds, and automated testing pipelines.

Note: This documentation is actively being maintained as the project develops. API contracts may change before stable release.

Quick Start

Send a POST request to the execution endpoint with your code and language:

POST /api/execute HTTP/1.1 Content-Type: application/json { "language": "python", "code": "print('Hello, Sandbox!')", "timeout": 10, "memory_limit": "256m" }

Response:

{ "status": "success", "exit_code": 0, "stdout": "Hello, Sandbox!\n", "stderr": "", "execution_time_ms": 142, "memory_used_mb": 12.4, "container_id": "psa-a1b2c3d4" }

Installation

Prerequisites: Python 3.12+, Docker Engine, pip.

# Clone the repository git clone https://github.com/your-repo/polyglot-sandbox-automator.git cd polyglot-sandbox-automator # Install dependencies pip install -r requirements.txt # Start the API server uvicorn main:app --host 0.0.0.0 --port 8000 --reload

POST /api/execute

Submit code for execution inside an isolated Docker sandbox.

Parameters: language string required "python" | "cpp" | "java" code string required Source code to execute timeout integer optional Max execution seconds (default: 30) memory_limit string optional Docker memory limit (default: "256m")

GET /api/languages

Returns a list of supported languages and their Docker image mappings.

{ "languages": [ { "id": "python", "version": "3.12", "image": "python:3.12-slim" }, { "id": "cpp", "version": "14", "image": "gcc:latest" }, { "id": "java", "version": "21", "image": "openjdk:21-slim" } ] }

Sandbox Design

Each execution request spawns a new, ephemeral Docker container. The container has no network access, a read-only filesystem (except for the injected code file), and is governed by Linux cgroups for CPU and memory resource enforcement.

After execution completes (or the timeout fires), the container is unconditionally removed. No execution state persists between runs.

Resource Limits

Default limits per container: CPU: 0.5 cores (--cpus=0.5) Memory: 256 MB (--memory=256m) Timeout: 30 seconds Network: disabled (--network=none) PID limit: 64 (--pids-limit=64)

Security Model

The sandbox uses Docker's default seccomp profile and drops all Linux capabilities except those needed for execution. User code runs as a non-root user inside the container. Combined with network isolation and cgroup limits, this provides a reasonable security boundary for untrusted code execution.

Warning: PSA is not intended for production use with fully untrusted code without additional hardening. Consider gVisor or Kata Containers for higher security requirements.

Key Learnings

Building PSA surfaced several important architectural and operational lessons:

  • Docker image pull latency is a major contributor to cold-start time. Pre-warming images on startup is essential.
  • cgroups v2 behavior differs significantly from v1 in how memory limits are enforced and reported.
  • FastAPI's async architecture pairs naturally with Docker SDK's async client for non-blocking execution handling.
  • PID limits are critical — without them, fork bombs can exhaust the host's process table even within a container.
  • Seccomp filtering adds measurable security with minimal performance overhead (typically <3%).

Challenges

The most significant technical challenge was handling timeout enforcement reliably. A naive asyncio.wait_for approach failed for C++ programs that caught SIGTERM. The final solution combines Docker's stop_timeout parameter with a fallback kill() after a grace period.

Future Work

  • WebSocket support for streaming stdout in real-time
  • Execution queue with priority scheduling
  • Additional language support: Go, Rust, JavaScript (Node.js)
  • Metrics dashboard with Prometheus + Grafana integration
  • Container pre-warming pool to minimize cold-start latency
